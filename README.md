# Zip2Learn

**証拠付き DFIR 教材生成基盤**

実データを、**証拠・引用元・時系列を保持した教材**へ変換する再利用可能な基盤です。
配布 ZIP を**展開せず・実行せず**に読み取り、ログの 1 行 1 行を根拠にして、
攻撃の時系列をたどる段階式の演習と最終調査レポートを作ります。

やることは四つです（ログ教材）。

1. 配布 ZIP を展開せずに中身を確認する
2. データセット形式（プロファイル）を判定し、問題ログ・平常時ログ・問題文・ツール・
   対象外に分ける。形式が分からなければ**汎用解析**として続ける
3. 同梱の案内にあるパスワードを、**利用者が押したときだけ**使って問題ログを読む
4. 登録済みのパーサーでログを共通の形（正規化イベント）へ直し、それを根拠に
   段階式の設問と最終調査レポートを作る

自動生成された四択に答えるのではなく、**ログを証拠として攻撃の全体像を
組み立てる調査体験**を目指しています。

もう一つの入口として、**Ghidra で解析して保存した `.gzf` ファイルから、静的解析の
演習**を作れます。関数・命令・文字列・参照といった保存済みの解析情報を根拠に、
「この命令が参照する文字列は？」「この呼び出し命令の行き先は？」を読み解きます。
Ghidra の処理だけを手元の Docker に任せ、**対象のプログラムは実行しません**
（[Ghidra ファイルから演習を作る](#ghidra-ファイルから演習を作る)）。

---

## 対象ユーザー

- DFIR を学び始めた人、ログ解析の進め方にまだ慣れていない人
- 手元のデータセットで演習を作りたい教員・チューター、勉強会の進行役

InfoTrace Mark II や MITRE ATT&CK の知識は前提にしません。

## 何に対応していて、何に対応していないか

| 項目 | 状況 |
|---|---|
| 読み取れるログ形式（パーサー） | **InfoTrace Mark II（ITM2）と Proxy（Squid 形式）の 2 つだけ** |
| それ以外の形式 | **自動では対応しません。** 新しい形式にはパーサーの実装が必要です |
| データセット形式（プロファイル） | **標準では 1 件も同梱していません。** 起動時に外部から追加できます |
| プロファイルが無い・当たらないとき | 汎用解析（プロファイル未特定）として、登録済みのパーサーで形式を自動判定します |

- プロファイルは、データセットのパスの形と役割を宣言する JSON です。
  実データ・正解・パスワードは書きません。
- パーサーは登録方式で追加できます。教材生成（`backend/explain.py`）を変更する
  必要はありません。
- 分類はできたが専用のパーサーが無いログは、無視せず「専用解析が未対応」として
  画面と教材に理由付きで表示します。教材の材料にはしません。形の似た既存の
  パーサーへ流し込むと、別の意味の記録をもっともらしく間違えて教材化するためです。
- どのパーサーでも読めなかったログは「形式を判別できなかったログ」として表示します。
- **Proxy は、プロファイルの `parsers` に `proxy` と明示したときだけ使います。**
  共通ログ形式の行は Web サーバーのアクセスログと同じ形で、宛先を丸ごと書いた
  要求（`GET http://…`）も Web サーバーが受け付けうるため（RFC 9112 §3.2.2）、
  内容だけでは「端末から外への通信」か「外からサーバーへの要求」かを決められ
  ません。プロファイル未特定（汎用解析）では、Proxy 形の行を含むログを教材の
  材料にせず、「通信の向きを断定できないログ」として理由付きで表示します。

追加の方法は **[docs/データセット教材基盤_開発者ガイド.md](docs/データセット教材基盤_開発者ガイド.md)**
にまとめてあります（プロファイル JSON のスキーマ、外部プロファイルの読み込み、
パーサーの登録、正規化イベントの契約、実データ統合テスト）。

## 安全性の方針

- **実行しない。** ZIP 内のプログラム、スクリプト、マクロ、検体を起動しません。
  GZF から演習を作る場合も、入力に含まれるプログラム・スクリプト・拡張は
  実行しません（動くのはアプリ、Docker、Java、Ghidra と、開発側が用意した固定の
  抽出スクリプトだけです）。
- **ZIP を展開しない。** ログ教材の作成では、ZIP の中身をディスクへ書き出さず、
  メモリ上で読みます。ディスクに書くのは、索引と作った教材（ローカルの DB）だけです。
  例外は GZF の処理で、選んだ `.gzf` 1 件だけを、アプリが決めた固定名で
  ジョブ専用の一時領域へ写します。この写しは処理が終わりしだい削除します。
- **入力データを外部へ送らない。** ログ・ZIP・GZF の処理は手元で完結し、外部の
  解析サーバーへは送りません。URL からの取得は `MWS_INTAKE_ENABLED` を明示的に
  設定しない限り無効です。ただし、GZF 機能の**初回準備**ではベースイメージと
  Ghidra の公式配布物をインターネットから取得します（入力ファイルの処理中は
  コンテナのネットワークを切っています）。
- **127.0.0.1 でしか待ち受けない。** 起動ごとにランダムな高位ポートを選び、
  `Host` ヘッダーを完全一致で検査します。
- **パスワードを残さない。** 同梱案内から読み取った値も手入力した値も、
  その 1 回の要求の間だけメモリに置きます。DB・ログ・URL・API 応答・例外文の
  どこにも残しません。
- **読めないものを安全と言わない。** 暗号化、破損、未対応方式は、安全側に
  倒して「読み取れないため教材化できない」と表示します。
- **プロファイルの場所を HTTP から指定させない。** 外部プロファイルは、
  サーバー起動時の環境変数でだけ受け付けます。
- **実データはリポジトリに入れない。** テスト用データは、テストのために作った
  名前・文書用のアドレス・無害なコマンドで組み立てます（詳しくは「実データの取り扱い」）。

## 必要環境

### 現在のアプリ

- **Python 3.10 以降**。アプリ本体の起動に必要です。利用する PC にインストールしてください。
  追加の Python パッケージは不要です。標準ライブラリだけで動きます。
- ブラウザ（Safari または Chrome の最新版）
- テストの一部で、暗号化 ZIP を作るために OS の `zip` コマンドを使います。
  無い環境では、その項目だけ自動で skip されます。

### Ghidra ファイルからの教材生成（使う場合だけ）

**既存のログ教材生成には Docker は不要です。** Docker が無くても、アプリは起動し、
ログ教材はこれまでどおり作れます。GZF から演習を作る場合だけ、次が必要です。

- **Docker。** Mac / Windows は [Docker Desktop](https://docs.docker.com/get-started/get-docker/)、
  Linux は Docker Desktop か [Docker Engine](https://docs.docker.com/engine/) を導入し、
  起動しておいてください。Mac は [公式導入手順](https://docs.docker.com/desktop/setup/install/mac-install/)
  に従い、Apple Silicon / Intel に合ったものを選びます。Mac で Docker Engine だけを
  直接使う方法はありません（Docker Desktop が必要です）。
  アプリが Docker を自動で導入したり、利用条件へ自動で同意したりはしません。
- **Python 3.10 以降**（アプリ本体。Docker の中では動かしません）。
- Ghidra と Java（JDK）は、アプリが作る処理イメージの中に入ります。
  **PC へ Ghidra や Java を別に入れる必要はありません。**
- 初回の「処理環境を準備する」で、インターネットから約 570 MB の Ghidra 公式配布物と
  JDK 入りのベースイメージを取得します。空きディスクは 4 GB 以上を目安にしてください
  （見積もりです。実測の状況は下の「確認状況」にあります）。
- 対応を確認した OS・CPU は、下の「確認状況」の表のとおりです。Docker は CPU の違いを
  自動では消さないので、`arm64`（Apple Silicon）と `amd64`（Intel / 多くの Windows・Linux）は
  別々に確認しています。

## 起動方法

```bash
python3 backend/api.py
```

データセット形式（プロファイル）を追加する場合は、起動時にフォルダを指定します。

```bash
DATASET_PROFILE_DIR=/path/to/profiles python3 backend/api.py
```

起動すると、次のような行が表示されます。

```
  Zip2Learn  ->  http://127.0.0.1:53421/
  role: instructor  (full access - this is your own machine)
  profiles: 0 loaded  (parsers: itm2, proxy)
  Ctrl+C to stop.
```

**表示された `http://127.0.0.1:...` の URL を、そのままブラウザで開いてください。**
ポート番号は起動のたびに変わります。決め打ちの `localhost:8000` では開けません。

読み込めなかったプロファイルは、`[profile] ファイル名: 理由` の形で表示されます
（中身は表示しません）。

終了するときは、実行中の端末で `Ctrl+C` を押します。

### やってはいけない開き方

- **`python3 -m http.server` は使わないでください。** 静的ファイルしか配れないため、
  ZIP の読み取り・形式の判定・教材生成がすべて動きません（この道具の中身は
  `backend/api.py` にあります）。
- **`index.html` を直接開かないでください。** `file://` ではブラウザが読み込みを
  遮断します。警告は出ず、白い画面になるだけで原因が分かりません。

### 学習者へ渡すとき（任意）

既定の権限は `instructor`（自分の端末で自分のデータを読む人）です。
読み取り専用にして渡す場合:

```bash
mkdir -p ~/.config/mws && echo student > ~/.config/mws/role
```

戻すときは `rm ~/.config/mws/role` です。これは事故防止の仕組みであって、
本人の操作を制限する境界ではありません（同じ利用者なら書き換えられます）。

## 基本操作

1. ブラウザで、起動時に表示された URL を開く。
2. ホームの**「ZIPファイルの中身を調べる →」**を押す。
3. **「フォルダを選ぶ…」**（または入力欄＋「このパスを読み取る」）で、配布 ZIP が
   入っている**フォルダ**を選ぶ。ZIP ファイル 1 個ではなく、その入れ物の
   フォルダを選びます。ZIP は開かず、目録だけを読み取ります。
4. 読み込み済み一覧から、調べたい ZIP を開く。
5. 画面下の**「データセットから教材を作る」**欄で、判定されたデータセット形式、
   一致度、読み取れるログ形式、問題ログ・平常時ログ・問題文・ツール・対象外の
   分類を確認する。
   - 判定が違うときは、同じ欄の**「データセット形式を指定する」**で選び直せます。
     指定した場合は「利用者が指定した形式」と表示されます。
   - プロファイルが 1 件も無いとき、または当たらないときは
     「プロファイル未特定（汎用解析）」と表示されます。
6. **「同梱の案内を使って読み取る」**を押す（汎用解析のときは
   **「汎用解析で教材を作る」**）。案内が見つからない場合は
   「パスワードを手入力する」欄を開きます。
7. **「演習を開く」**→ **「調査を始める」**→ 段階ごとに証拠を読み、設問に答える。
8. 回答後に出る**「根拠ログを見る: <ファイル名> <行番号> 行目」**で、
   その行の証拠カードへ飛べる。
9. 最後に最終調査レポート（時系列・得点・ATT&CK・未確定事項）を確認し、
   **「演習一覧へ戻る」**。

設問で迷ったときは **「ヒントを見る」** を開くと、見るべき項目や読み方を
確認できます。ヒントを見ても減点されません。新しく生成するログ読解問題には
実際の項目名が入り、保存済みの教材にヒントが無い場合は共通の読み方を表示します。
項目名付きのヒントを保存済み教材にも付けるには、元の ZIP から教材を再生成してください。

データセット画面・導入画面・最終レポートには、同じ 1 行
（`データセット形式: <名前>（<edition>）／自動で判定した形式`）が出ます。
edition の無い形式では括弧を付けません。

## Ghidra ファイルから演習を作る

Ghidra で解析して保存した `.gzf` ファイルから、静的解析の演習を作ります。
利用者の操作は**ファイルを選んで「演習を作成する」を押すところまで**です。
Ghidra の起動や JSON の書き出しは求めません。

### 初回の準備（一度だけ）

1. Docker（Docker Desktop など）を起動する。
2. いつもどおり `python3 backend/api.py` でアプリを起動し、表示された URL を開く。
3. ホームの **「Ghidraファイルから演習を作る →」** を押す。
4. 「処理環境」の欄で Docker の状態を確かめる。未導入・停止中・接続先がこの PC の外・
   準備済み、のどれかが表示されます。
5. 「処理環境がまだありません」と出たら **「処理環境を準備する」** を押す。
   固定したベースイメージと Ghidra 12.1.4 の公式配布物を取得し、この PC の Docker の中で
   処理イメージを組み立てます（通信が必要です）。準備とファイルの処理は別の操作です。

### 演習を作る（`.gzf` を直接選ぶ）

1. 「GZF ファイル」で `.gzf` を選ぶ。
2. **「演習を作成する」** を押す。「ファイル確認中」→「Ghidra で読み取り中」→
   「教材生成中」の順に進みます。途中で **「キャンセル」** できます。
3. 完了したら **「演習を始める」**。導入画面 → 段階ごとの設問 → 振り返りと進みます。

まず試すときは **「同梱サンプル（termmines）で試す」** を押してください。
termmines は Ghidra の公式教材に含まれる端末版マインスイーパーで、**マルウェアでは
ありません**（来歴は [ghidra/sample/PROVENANCE.md](ghidra/sample/PROVENANCE.md)）。

### ZIP の中の `.gzf` から作る

既存の「ZIPファイルの中身を調べる」でフォルダを読み取り、ZIP を開くと、`.gzf` の項目に
**「この GZF から演習を作る」** が出ます。押した 1 件だけを処理します（一覧の表示や
「先頭のデータを見る」だけでは Docker を起動しません）。

- 対応する入れ子は **1 段まで**（`外側.zip` の中の `内側.zip` の中の `.gzf`）です。
- ZipCrypto で暗号化された項目は、その場でパスワードを入力して読みます。
  パスワードはその要求の間だけメモリに置き、保存も記録もしません。
  **AES 方式は未対応**です（推測や総当たりはしません）。
- 同じ名前の項目が複数あっても、目録の位置で区別します。同じ名前の入れ子 ZIP が
  複数あるときは、どれの中身か決められないため断ります。
- シンボリックリンク、絶対パス・`..`・制御文字を含む名前、極端な圧縮率の項目は断ります。
- ZIP を読み込んだ後に書き換えられていたら断ります（読み込み時の SHA-256 と照合します）。

### `.gzf` の用意の仕方（Ghidra 側）

Ghidra でプログラムを取り込み、**Analyze（自動解析）を実行してから**、
File → Export Program で形式に「Ghidra Zip File」を選んで保存します。
解析していない GZF は、理由を示して断ります（アプリ側で黙って再解析はしません）。
固定している Ghidra 12.1.4 より新しい版で作った GZF は読めないことがあります。

### 何を動かし、何を動かさないか

- **動かすもの:** アプリ（Python）、Docker CLI、アプリが作った固定の処理イメージ、
  その中の Java と Ghidra（Headless モード）、開発側が用意した固定の抽出スクリプト
  （[ghidra/image/ExtractStaticFacts.java](ghidra/image/ExtractStaticFacts.java)）。
- **動かさないもの:** 入力の中の対象プログラム（起動・関数の呼び出し・デバッガ接続）、
  命令や P-code のエミュレーション、元の検体の復元・書き出し（Original File など）、
  入力の ZIP・GZF に同梱されたスクリプト・拡張・設定、自動解析のやり直し、逆コンパイル。
- Ghidra は `-loader GzfLoader -noanalysis -readOnly` の固定引数で起動し、実行する
  スクリプトは上の 1 本だけです。`-noanalysis` は自動解析を止めるもの、`-readOnly` は
  保存を止めるもので、**それ自体は任意のスクリプトを防ぐサンドボックスではありません**。
  そのため、起動引数を固定し、下のとおりコンテナを隔離しています。
- それでも、細工された入力で Ghidra・Java・Docker の脆弱性が突かれる可能性まで
  ゼロにはできません。「対象を実行する機能・経路を作らない」ことと、隔離・上限・
  テストを重ねることで危険を下げています。出所の分からない GZF は慎重に扱ってください。

### 処理コンテナの制限（実値）

| 項目 | 値 |
|---|---|
| ネットワーク | なし（`--network=none`）。取得済みイメージだけを使う（`--pull=never`） |
| 実行ユーザー | アプリを起動した利用者の uid/gid（root では起動しません） |
| 権限 | `--cap-drop=ALL`、`no-new-privileges`、`--privileged` は使わない |
| ファイルシステム | ルートは読み取り専用。書き込めるのは `/tmp`（tmpfs 1536 MB、noexec）だけ |
| 共有するホスト領域 | ジョブ専用の入力ディレクトリ 1 つを読み取り専用で。HOME・ソース一式・Docker ソケットは共有しない |
| メモリ / CPU / プロセス数 | 4 GB（スワップなし）/ 2 コア / 256 |
| ログ | コンテナログは保存しない（`--log-driver=none`）。受け取る出力は JSON 32 MB・エラー 64 KB まで |
| 時間 | 1 回 600 秒（コンテナ起動から抽出の終わりまで全体） |
| 入力 | GZF 64 MB まで、展開後 512 MB まで、同時に 1 件 |
| 接続先 | この PC の UNIX ソケット（Windows は名前付きパイプ）だけ。TCP・SSH・確かめられない接続は断る |

### 固定している版

| 部品 | 版 |
|---|---|
| Ghidra | 12.1.4（`ghidra_12.1.4_PUBLIC_20260921.zip`、SHA-256 `ddac49f903da9d5bac833e5cc79395098b9c33cfd3279be5f31bd00387d2d4db`） |
| ベースイメージ（JDK 21） | `eclipse-temurin:21.0.12.1_1-jdk-noble@sha256:d1eb0297924c2d5a37ba7042a59ae84a3487e086b077ac054019a423767d4311` |
| 抽出スクリプト | 1.0.0（ファイルの SHA-256 は画面の「固定している版と上限」に表示） |
| 処理イメージ | `mws-ghidra-static:12.1.4-<build context の指紋>`（手元でビルド。公開イメージは使いません） |

イメージは手元の Docker でだけ組み立てます（`--builder default` を明示し、その builder が
ローカルの `docker` driver であることを確かめます。クラウドの builder へは送りません）。
build context は [ghidra/image/](ghidra/image/) の 4 ファイルだけです。
作った教材の導入画面に、使った Ghidra・スクリプトの版とイメージ ID、入力 GZF の
SHA-256 が記録されます。版が変われば、同じ GZF から同じ教材になるとは限りません。

### 保存されるものと消し方

| もの | 置き場所 | いつ消えるか |
|---|---|---|
| 入力 GZF の写し | `.mws-state/ghidra-jobs/<ジョブ>/` | 処理の終了時（成功・失敗・キャンセル・期限切れ）。異常終了した場合は次の起動時 |
| Ghidra の一時プロジェクト・抽出 JSON | コンテナ内の tmpfs | コンテナの終了時（`--rm`） |
| 処理コンテナ | Docker | 終了時。残った場合は次の起動時に、この導入先のラベルが付いた、前回以前の起動のものだけを消します（今回の起動で始めた処理は止めません） |
| 作った教材（採用した根拠・版・ハッシュ） | `.mws-state/manifest.sqlite3` | 教材の導入画面の「この教材を削除する」で消せます |
| 処理イメージ | Docker | 使わなくなったら `docker image rm mws-ghidra-static:<タグ>`（タグは画面に表示） |

パスワード、ファイルの中身、手元の絶対パスは、通常のログや画面のエラーに出しません。
コンテナの生のエラー文は利用者に返さず、固定の理由と文言に置き換えます
（開発時の調査用に、`MWS_GHIDRA_DEBUG=1` を付けて起動したときだけ、手元の端末へ診断を出します）。

### 困ったとき

| 表示 | すること |
|---|---|
| Docker が見つかりません / 起動していません | Docker を導入・起動して「状態を確認し直す」。**ログ教材は Docker なしでそのまま使えます** |
| 接続先がこの PC の外を向いています | `DOCKER_HOST` を外すか、`docker context use` でこの PC の Docker に戻す |
| 処理環境が古い版です | 「処理環境を準備する」で作り直す |
| GZF として読めません / 版が読めない形式です | Ghidra で Export Program（Ghidra Zip File）をやり直す。新しすぎる版の GZF は読めないことがあります |
| 解析済みとして保存されていません | Ghidra で Analyze を実行してから保存し直す |
| ファイルが大きすぎます / 上限を超えました | 対象を小さくする。**上限や安全のための制限を緩めることは解決策にしないでください** |
| 根拠の揃う設問を作れませんでした | 表示された理由を確認する（文字列や関数が少ないプログラムでは設問が減ります） |
| ディスクの空きが足りません | 空きを作ってから再実行する |
| キャンセルしました | 作業データは削除済みです。そのままやり直せます |

#### 実測値（2026-09-27、Apple Silicon の Mac、Docker Desktop / Engine 29.8.0）

| 項目 | 値 |
|---|---|
| 初回準備の取得量 | Ghidra 配布物 約 570 MB（取得 約 41 秒）＋ベースイメージ（取得・展開 約 9 秒）。回線により変わります |
| 処理イメージのディスク使用量 | 3.34 GB（`docker image ls` の DISK USAGE） |
| 準備の作り直し（取得済みのキャッシュあり） | 約 20 秒 |
| サンプル 1 件の処理（コンテナ起動から教材まで） | 約 3〜3.5 秒 |
| 処理中のコンテナのメモリ | 約 130〜150 MiB（`docker stats` の観測 1 回ずつ。上限は 4 GB） |
| 処理中のコンテナの CPU | 最大 約 180%（2 コアの上限の内側） |
| サンプル GZF の作り直し（開発者のみ） | コンパイル 約 17 秒（amd64 のエミュレーション）＋解析 約 4 秒 |

処理が約 3 秒と短いため、`docker top` によるプロセスの観測は 1 回の処理につき 2 回程度です。
観測した範囲では、コンテナ内で動いたのは `run-extract.sh`・`bash`・`java` だけで、
対象のプログラムや入力のパスが実行ファイルとして現れることはありませんでした。観測の間に
一瞬だけ動いたプロセスまでは捉えきれない可能性があります。対象を実行しないことの主な根拠は、
固定の抽出スクリプトと起動引数の監査（`backend/tests/test_ghidra_audit.py`）です。

Ghidra 12.1.4 の公式配布物には linux/arm64 用の逆コンパイラ（ネイティブ部品）が含まれていません。
アプリの抽出は逆コンパイラを使わないので影響はありませんが、Apple Silicon で GZF を作り直す場合
（同梱サンプルを含む）は、逆コンパイラを使う一部の自動解析（呼び出し規約の分析など）が行われません。

## テストの実行方法

```bash
python3 -m unittest discover -s backend/tests
node backend/tests/test_ui_evidence.mjs
node backend/tests/test_ui_report.mjs
node backend/tests/test_ui_dataset.mjs
node backend/tests/test_ui_wrapping.mjs
node backend/tests/test_ui_static.mjs
```

すべて実データなしで動きます。CI で実データを要求することはありません。
**Docker も不要です。** GZF 機能のテストは、Docker の応答を偽物に差し替え、
Ghidra と同じ並びで組んだ擬似 GZF と架空の抽出結果を使います
（`backend/tests/ghidra_fixtures.py`）。実際のコンテナでの確認は、次の手順で別に行います。

### 実コンテナでの確認（任意・Docker が必要）

```bash
python3 backend/tests/ghidra_live_check.py
```

処理イメージが準備済みであることを前提に、同梱サンプルを本番と同じ経路
（入力の写し → 固定コマンドのコンテナ → JSON の検証 → 教材生成）で処理し、
コンテナの設定（ネットワーク・マウント・ユーザー・権限・上限）を `docker inspect` で
確かめ、キャンセル時にコンテナが止まって消えることを確かめます。

### 実データを使う任意の統合テスト

手元に実データがある場合だけ、Git 管理外に置いたマニフェストを指定して
追加の確認を実行できます。

```bash
REAL_DATA_MANIFEST=/path/to/private-manifest.json \
  python3 -m unittest backend.tests.test_real_data -v
```

- `REAL_DATA_MANIFEST` を設定しなければ、この項目は自動で skip されます。
- マニフェストに書かれたパスだけを開きます。フォルダを探し回ることはしません。
- 失敗しても、パスワード・ログ本文・ZIP のメンバー名・プロファイル ID・期待値の
  数を出力しません。アーカイブはマニフェスト内の番号で呼びます。

マニフェストの書き方は開発者ガイドの 7 章にあります。

## 現在の制限

- 読み取れるログ形式は InfoTrace Mark II と Proxy（Squid 形式）の 2 つだけです。
  Proxy はプロファイルで明示したときだけ使うので、プロファイル 0 件の標準構成では
  通信の段階は作られません。
  Web サーバーのアクセスログ、Linux のシステムログなどは、パーサーを追加しない
  限り教材の材料になりません。
- 標準で同梱するプロファイルはありません。役割（問題ログ・平常時ログ・同梱の
  サンプルなど）を正しく分けるには、そのデータセット用のプロファイルが必要です。
  汎用解析では、平常時ログや同梱ツールのサンプルも教材の材料に混ざりえます
  （画面でそう警告します）。また、汎用解析は暗号化されたログを読み取りません
  （読めなかったログとして、名前と理由を教材に残します）。
- 汎用解析の読み取り上限は、1 回の生成で合計 24 MB、1 ログ 4 MB、入れ子 2 階層
  までです。内側の ZIP も読む前に予算を確保し、収まらないものは読みません。
  上限で切ったもの、読めなかったものは、導入と最終レポートの未確定事項に出します。
- PDF からのパスワード抽出には対応していません（`.md` と `.txt` のみ）。
- AES 方式で暗号化された ZIP は、標準ライブラリで読めないため読み取れません。
  「未対応の暗号方式」として表示します。
- 多重 ZIP を潜るのは 3 階層までです。それより深いものは未確認として表示します。
- 1 ログ 32 MB / 1 回の生成で合計 128 MB / 1 ログ 50 万行が読み取りの上限です。
  上限に達した場合は打ち切りを明示します。
- 生成される演習は**自動生成の下書き**です。授業や発表で使う前に内容を
  確認してください。
- 学習履歴の保存・再開、レポートのファイル出力、教員による問題編集は未実装です。
- GZF から作る演習は、単体の `.gzf`（Program）だけに対応します。`.gpr` / `.rep` の
  プロジェクト一式、`.gar`、`.fidb`、生の PE / ELF、ソースコードからの解析には
  対応しません。解析されていない GZF は再解析せずに断ります。
- GZF の設問は、文字列の参照・直接呼び出し・外部関数の 3 種類だけです。間接呼び出し、
  逆コンパイル結果、動的な挙動、悪性の判定、ATT&CK の対応付けは扱いません。
- 利用者が任意の Ghidra スクリプト・イメージ・Docker のオプションを指定する機能は
  ありません（意図的に作っていません）。

## 実データの取り扱い

**実データを、このリポジトリに追加しないでください。**

- 配布 ZIP、展開物、ログ本文、パスワード、正解、ハッシュ値のいずれも
  コミットしないでください。再配布条件に反することがあります。
- テスト用の fixture へ実データを写すこともしないでください。
  `backend/tests/` の fixture は、テストのために作った名前と値で組み立てています。
  アドレスや識別子は文書用の値（IPv4 は RFC 5737、IPv6 は RFC 3849、MAC は
  RFC 7042）か、テスト用と分かる合成値を使います。例外は次の 2 つです。
  - 通信制限のテスト（`test_net.py`）は、遮断すべき宛先・許すべき宛先の例として、
    広く知られた特殊用途・公開のアドレス（`169.254.169.254`、`8.8.8.8` など）を使います。
  - Ghidra 教材のテストの一部（`fixtures/ghidra/termmines-facts.json`）は、同梱サンプル
    termmines（Apache 2.0）から実際に抽出したデータです（THIRD_PARTY_NOTICES.md）。
- 2026-09-27 に、リポジトリ内の識別子の形をした値（SID・MAC・GUID・IP アドレス）を
  点検しました。出所を確かめられない値（ITM2 形式の長い行のテスト）は、同じ長さ・
  形式の合成値へ置き換えています。置き換えは出所を明らかにするものではなく、
  以前の値が実データだったかどうかは分かっていません。
- 特定のデータセット向けのプロファイルやマニフェストは、リポジトリの外、
  または Git 管理外の `.local-validation/`（`.gitignore` 済み）に置きます。
  `data/profiles/` へは置きません（テストが止めます）。
- `.mws-state/` はローカルの実行時状態（読み込んだ ZIP の索引）で、
  `.gitignore` 済みです。
