# データセット教材基盤 開発者ガイド

このアプリの中心は、**実データを、証拠・引用元・時系列を保持した教材へ変換する
基盤**です。この文書は、基盤へ新しいデータセット形式（プロファイル）やログ形式
（パーサー）を足す開発者向けに、決まりごとをまとめたものです。

- 対応済みのパーサーは **InfoTrace Mark II（`itm2`）と Proxy（`proxy`）の 2 つだけ**です。
- 任意の形式へ自動で対応するわけではありません。新しい形式には、パーサーの実装が必要です。
- 公開版はプロファイルを **1 件も同梱していません**。0 件でも汎用解析として動きます。

---

## 1. 責務の分け方

```text
アーカイブ読み取り        backend/archive.py, backend/dataset.py
    ↓  {論理パス: 本文}     （展開しない・実行しない・読み取り予算つき）
入力ソース               parsers.InputSource
    ↓
パーサーレジストリ        backend/parsers/registry.py（ParserRegistry）
    ↓
正規化イベント＋EvidenceStore   parsers.NormalizedEvent, evidence.EvidenceStore
    ↓
教材生成                 backend/explain.py（ログ形式を知らない）
    ↓
段階・設問・時系列・ATT&CK・最終レポート
```

| 層 | 知っていること | 知らないこと |
|---|---|---|
| プロファイル（JSON） | そのデータセットのパスの形、役割、使うパーサー ID | ログの読み方 |
| `dataset.py` | プロファイルの検証、役割の割り当て、暗号化ログの読み取り | 特定のデータセットの名前や ZIP 構造 |
| パーサー | 1 つのログ形式の読み方、その形式の説明文 | 教材の組み立て方 |
| `explain.py` | 正規化イベントの語彙（種別・動作・属性・照合キー） | ITM2 や Proxy の行の形 |
| 画面（`js/`） | API が返すプロファイル情報と教材 | 年度やデータセット固有の名前 |

教材生成へ渡る正規化イベントは、すべて `ParserRegistry.parse_sources()` を
通ります。`explain.py` には形式ごとの分岐（`if parser_id == "itm2"` の類）も、
`parsers.itm2` / `parsers.proxy` の import もありません（テスト
`test_parsers.TestLessonGenerationKnowsNoFormat` が確かめます）。

## 2. プロファイル JSON のスキーマ

プロファイルは「あるデータセットの ZIP が、どんな名前のファイルを持ち、それぞれが
教材の何にあたるか」を宣言する JSON です。**実データ・正解・パスワードは書きません。**

### 2.1 項目

| 項目 | 必須 | 型 | 意味 |
|---|---|---|---|
| `id` | ○ | 文字列 | 英数字・`-`・`_` で 1〜64 文字。API の `profileId` と同じ形 |
| `label` | ○ | 文字列 | 画面に出す名前（200 文字まで） |
| `edition` | | 文字列 | 版・時期・回など任意の区別。無ければ画面は括弧を付けない |
| `metadata` | | オブジェクト | 任意の説明。16 項目まで、キー 64 文字・値 500 文字までの文字列 |
| `order` | | 整数 | 選択肢の並び順。小さいほど先。無ければ `label`、`id` の順で後ろ |
| `match.requiredPathPatterns` | ○ | パターン配列 | すべて当たらなければ、このプロファイルと判定しない。1 個以上必要 |
| `match.optionalNamePatterns` | | パターン配列 | 当たった割合が一致度になる。半分以上当たらなければ断定しない |
| `roles` | | オブジェクト | 役割 → パターン配列。役割は下の表のとおり |
| `parsers` | | 文字列配列 | 使うパーサー ID。省略すると、自動判定に参加するパーサー（`AUTO_DETECT`）で判定。`proxy` はここで明示したときだけ使われる |
| `unsupportedFormats` | | 配列 | 分類はするが専用解析の無いログ（`label`・`detail`・`patterns`） |
| `passwordHintPatterns` | | パターン配列 | パスワードの案内文を探すファイル |
| `passwordFilePatterns` | | パターン配列 | 中身そのものがパスワードであるファイル |
| `passwordHintContainerPatterns` | | パターン配列 | 案内文を探すために開いてよい内側 ZIP（最大 4 個） |

**`year` は使えません。** 書くと「`edition` を使ってください」という理由付きで
拒否します。年度という特別な型や意味は、中心のモデルにありません。

表にない項目も拒否します。綴りを間違えた項目を黙って無視すると、「書いたのに
効かない」の原因が分からなくなるためです。

役割（`roles` のキー）:

| 役割 | 意味 | 教材の材料に |
|---|---|---|
| `challenge` | 本番の問題ログ | する |
| `baseline` | 平常時・サンプルログ | しない（比較用として区別） |
| `narrative` | 問題文・説明資料 | しない |
| `tool` | 同梱ツールとそのサンプル | しない |
| `artifact` | 静的解析の対象 | しない（実行もしない） |
| `unrelated` | 対象外 | しない |
| `ignore` | `__MACOSX` など | 表示もしない |

どれにも当たらなかったものは `unknown` になります（宣言はできません）。
役割は `ignore → tool → challenge → baseline → artifact → narrative → unrelated`
の順に当て、先に当たったものを採ります。

### 2.2 パターンの書き方

- `fnmatch` 形式（`*` と `?`）で、大文字・小文字を区別します。
- 多重 ZIP の中身は `外側の名前 :: 内側の名前` の論理パスで表します。
  例: `*/evidence/logs.zip :: logs/*.log`。潜るのは 3 階層までです。
- 照合の前に名前を Unicode NFC へそろえます（macOS が作る ZIP の NFD 名対策）。

### 2.3 自動判定の決まり

1. `requiredPathPatterns` がすべて当たるプロファイルだけが候補です。
2. `optionalNamePatterns` の当たった割合が一致度（0〜1）です。0.5 未満は断定しません。
3. 首位が同点なら、どれとも断定せず汎用解析へ回し、候補名を警告に出します。
4. どれにも当たらないのは正常系です。**プロファイル未特定（汎用解析）** として続けます。

利用者は画面の「データセット形式を指定する」で上書きできます。その場合、画面・
導入・最終レポートのすべてに「利用者が指定した形式」と出ます（`forced: true`）。

### 2.4 例

`backend/tests/fixtures/profiles/example-incident.json`（テスト用の架空の形式）:

```json
{
  "id": "example-incident",
  "label": "Example incident logs",
  "edition": "fixture v1",
  "order": 10,
  "metadata": { "producer": "test suite" },
  "match": {
    "requiredPathPatterns": ["*/evidence/logs.zip"],
    "optionalNamePatterns": ["*/reference/baseline.zip", "*/tools/sample.log"]
  },
  "roles": {
    "tool": ["*/tools/*", "*/tools/* :: *"],
    "challenge": ["*/evidence/logs.zip", "*/evidence/logs.zip :: *"],
    "baseline": ["*/reference/baseline*.zip", "*/reference/baseline*.zip :: *"],
    "narrative": ["*/*.md", "*/*.txt"]
  },
  "passwordHintPatterns": ["*/*.md", "*/*.txt"],
  "parsers": ["itm2", "proxy"]
}
```

## 3. 外部プロファイルの読み込み

プロファイルは、**サーバーの起動時の設定としてだけ**追加できます。HTTP リクエスト
からローカルのフォルダを指定させることはしません。

```bash
DATASET_PROFILE_DIR=/path/to/profiles python3 backend/api.py
```

- 複数のフォルダは OS のパス区切り（macOS・Linux では `:`）で並べます。
- 読むのは、そのフォルダ直下の `*.json` だけです（1 件 256 KB まで）。
- 標準のフォルダ `data/profiles/` も読みますが、公開版では空です。

読み込めなかったものは黙って捨てず、**ファイル名と理由だけ**を報告します
（中身は引用しません）。

| 状況 | 扱い |
|---|---|
| JSON として読めない・スキーマ違反・`year` がある | そのファイルを拒否して報告 |
| 同じ `id` が 2 つ以上 | **どのコピーも読み込まず**、それぞれ報告 |
| `parsers` に未登録の ID | プロファイルは読み込み、未登録の ID を報告（その形式は解析しない） |
| 指定したフォルダが無い | 設定の誤りとして報告 |
| プロファイルが 0 件 | 正常。汎用解析で動き、画面の選択欄は出さない |

報告は、起動時の端末（`[profile] ファイル名: 理由`）、`GET /api/status` の
`profiles.errors`、データセット画面の「読み込めなかったプロファイル」欄に出ます。

特定のデータセット向けのプロファイルは、リポジトリの外（または Git 管理外の
フォルダ）に置いてください。`data/profiles/` へは置きません（テスト
`test_profile_schema.TestPublicBoundary` が止めます）。

## 4. パーサーの追加

### 4.1 変更する場所

新しいログ形式に対応するときに触るのは、次の 2 か所（とテスト）だけです。

1. **`backend/parsers/<形式名>.py` を新しく作る** — `parsers.Parser` の派生クラス
2. **`backend/parsers/__init__.py` の `REGISTRY` に 1 行足す** — 登録

`explain.py`（`build_lesson`）、`api.py`、`dataset.py`、画面は変更しません。
プロファイルでその形式だけを使わせたい場合は、プロファイルの `parsers` に ID を
書きます（省略すれば自動判定の候補に自動で入ります）。

### 4.2 最小の例

```python
# backend/parsers/example.py
import timeline
from .base import InputSource, NormalizedEvent, Parser, clean_host_keys, source_of


class ExampleParser(Parser):
    id = "example"                       # 小文字の英数字・-・_
    label = "Example（端末の記録）"         # 画面に出す名前

    def detect(self, source: InputSource) -> float:
        # 0〜1。0 なら parse() は呼ばれない。先頭の数行だけを見る。
        return 1.0 if source.text.startswith("EXAMPLE|") else 0.0

    def parse(self, source, evidence_store=None):
        events = []
        for no, line in enumerate(source.lines(), 1):     # 行番号は 1 から
            parts = line.split("|")
            if len(parts) != 5 or parts[0] != "EXAMPLE":
                continue
            _, ts, host, program, args = parts
            events.append(NormalizedEvent(
                kind="process", action="start",
                timestamp=timeline.UNKNOWN,                # 読めたら timeline.stamp(...)
                host=host or "?",
                summary=f"{host} で {program} が起動",
                source=source_of(source.name, no, line),   # 出典・行番号・原文
                parser_id=self.id,
                attributes={"program": program,
                            "program_name": program.rsplit("\\", 1)[-1]},
                correlation_keys=clean_host_keys([host]),
            ))
        return events
```

```python
# backend/parsers/__init__.py
REGISTRY = ParserRegistry([itm2.PARSER, proxy.PARSER, example.ExampleParser()])
```

これだけで、プロファイル未特定のときの自動判定にも、教材生成にも届きます
（テスト `test_parsers.TestDummyParserReachesTheLesson` が、テストの中で登録した
ダミーのパーサーだけで教材ができることを確かめています）。

### 4.3 任意の追加（教材の質が上がる）

| 項目 | 役目 | 省略したとき |
|---|---|---|
| `reread(kind, fact, excerpt)` | 保存済みの抜粋から事実を読み直し、`FactReading(値, 項目名)` を返す | その事実を問う設問と ATT&CK の対応付けは作られない。通信の要求元の設問も含め、正解は必ず読み直した値から取る（抜粋は 1000 文字で切れるので、属性にある値でも引用に無ければ使わない） |
| `FACT_TEXTS` | `(種別, 事実) → FactText(where, next)`。設問の解説の書き出し。`{field}` は実際に読んだ項目名に置き換わる | 既定の文言 |
| `RECORD_NOUNS` | 種別 → この形式の記録の呼び名（段階の導入文） | 既定の呼び名 |
| `ABOUTS` | 種別 → この形式の記録が何を残すかの一文 | その一文を出さない |

`reread()` が尋ねられる事実は `parsers.FACTS` にあります
（`process`: `program_name`・`command_line`・`host`、`file`: `path`・`host`、
`registry`: `path`、`network`: `client`・`target`）。ATT&CK の対応付けは、
パーサーが読み直した事実（`FactReading`）からだけ行い、理由には実際に読んだ
項目名が入ります。要約文や属性から推測はしません。

### 4.4 登録簿が守ること

- 同じ ID の二重登録は `ContractError` で拒否します。
- パーサーは常に ID 順に試し、入力ソースは名前順に読みます。登録の順序で結果は変わりません。
- `detect()` の値は 0〜1 の数か真偽値でなければなりません。
- `detect()` は、その形式だと**言い切れるときだけ** 0 より大きい値を返します。
  行の形が似た別の形式があるなら、意味の違いが出る書き方で区別してください。
- 内容だけではどうしても言い切れない形式は、クラス属性 `AUTO_DETECT = False` に
  します。自動判定（プロファイルが `parsers` を指定しないとき）の候補から外れ、
  プロファイルの `parsers` で明示されたときだけ使われます。読めそうだったのに
  使わなかった入力ソースは `ParsedSources.explicit_only` に残り、教材には
  「通信の向きを断定できないログ」として報告されます。
- 組み込みの Proxy は `AUTO_DETECT = False` です。共通ログ形式の行は Web サーバーの
  アクセスログと同じ形で、宛先を丸ごと書いた要求（`GET http://…`）も Web サーバーが
  受け付けうるため（RFC 9112 §3.2.2）、通信の向きを内容から決められません。
  明示されたときも、宛先を丸ごと書いた要求・`CONNECT host:443` だけを読み、
  パスだけの要求（`GET /index.html`）が混ざるログは読みません。
- `parse()` が返したものは 1 件ずつ検査し（5 章）、契約違反や例外があれば、
  その入力ソースについてそのパーサーの出力を**丸ごと**捨て、理由を記録します。
  例外文はログの中身を含みうるので、記録するのは例外の型名だけです。
- どのパーサーも読めなかった入力ソースは「形式を判別できなかったログ」として
  教材と画面に出ます。

### 4.5 やってはいけないこと

- `evidence_store` へ全行を登録しない。教材に載るのは一部の行だけで、登録は教材生成が
  必要な行についてだけ行います（全行を登録するとメモリが行数に比例して膨らみます）。
- 例外文やログへ、行の中身を載せない。
- `explain.py` にその形式の分岐を足さない。説明文が必要なら `FACT_TEXTS` 等で渡します。

## 5. 正規化イベントの契約

`parsers.NormalizedEvent`（不変の dataclass）。教材生成が受け取るのはこれだけです。

| 項目 | 型 | 決まり |
|---|---|---|
| `kind` | 文字列 | 小文字の種別名。段階に載るのは `process`・`file`・`registry`・`network`。それ以外も出せるが、件数の集計にだけ使う |
| `action` | 文字列 | 種別の中での動作（`start`・`create`・`request` など）。上の 4 種別では空にできない |
| `timestamp` | `timeline.Stamp` | `timeline.stamp(...)` で作る。読めなければ `timeline.UNKNOWN` |
| `host` | 文字列 | 表示用の端末名。読めなければ `?` など |
| `summary` | 文字列 | 1 行の要約。上の 4 種別では空にできない |
| `source` | `evidence.Source` | `source_of(論理パス, 行番号, 原文)` で作る。行番号は 1 以上 |
| `parser_id` | 文字列 | 作ったパーサーの ID。他のパーサーを名乗ると拒否 |
| `attributes` | 文字列 → 文字列 | 種別ごとの必須キーあり（下表）。値は空文字でもよい |
| `correlation_keys` | `frozenset` | 端末を照合する呼び名。`?`・`127.0.0.1`・`localhost` などの代用値は入れない（`clean_host_keys()` を通す） |
| `evidence_id` | 文字列 | **自動で計算**（出典と種別から）。引数では渡せない |

種別ごとの必須属性（`parsers.REQUIRED_ATTRIBUTES`）:

| 種別 | 必須の属性 |
|---|---|
| `process` | `program`, `program_name` |
| `file` | `path`, `name` |
| `registry` | `path` |
| `network` | `client`, `method`, `target` |

`evidence_id` を引数で受け取らないのは、出典と食い違う ID を作れないように
するためです。計算は `EvidenceStore.add()` と同じ関数なので、教材へ登録したときの
ID と必ず一致します。既存の教材の証拠 ID もこの計算で変わっていません。

時刻の比較基準（`Stamp.basis`）は、タイムゾーンつきなら `utc`、無ければ
`local:<論理パス>` です。相関の設問は、`correlation_keys` が重なり、比較基準が
同じで、時刻が近い `process`／`file` と外部宛ての `network` の組から作ります。

## 6. API とデータセット情報

| 要求 | 内容 |
|---|---|
| `GET /api/archives/<id>/dataset` | 自動判定の結果 |
| `GET /api/archives/<id>/dataset?profileId=<id>` | 利用者が形式を指定した結果（`forced: true`） |
| `POST /api/generate` `{"archive": 1}` | 自動判定で教材を作る |
| `POST /api/generate` `{"archive": 1, "profileId": "<id>"}` | 指定した形式で作る |

データセット情報（画面・教材の `lesson.dataset`・API で共通）:

```json
{
  "profileId": "example-incident",
  "label": "Example incident logs",
  "edition": "fixture v1",
  "metadata": {},
  "forced": false,
  "confidence": 1.0,
  "generic": false,
  "parsers": ["itm2", "proxy"],
  "parserLabels": ["InfoTrace Mark II（端末の記録）", "Proxy（通信の記録）"],
  "unknownParsers": []
}
```

プロファイル未特定のときは `profileId: null`、`generic: true`、
`label: "プロファイル未特定（汎用解析）"` です。`year` は返しません。

**非推奨の互換:** 旧名 `profile` を `profileId` の別名として受け付けます
（`api.Handler._legacy_profile_alias`）。現在の画面と新しいコードは使いません。
両方が来て食い違えば拒否します。この互換を外しても新しい契約が成り立つことは
`test_api.TestProfileIdContract` が確かめています。

## 7. 実データ統合テスト

公開のテストは実データを必要としません。手元の実データで確かめるときだけ、
**Git 管理外に置いたマニフェスト**を環境変数で渡します。

```bash
REAL_DATA_MANIFEST=/path/to/private-manifest.json \
  python3 -m unittest backend.tests.test_real_data -v
```

変数が無ければ `TestRealDataManifest` は skip します。

### 7.1 マニフェストの形式

```json
{
  "profileDirs": ["../profiles"],
  "archives": [
    {
      "path": "/path/to/dataset-a.zip",
      "profileId": "site-profile-a",
      "credential": "embedded",
      "requireBaseline": true,
      "requireTool": true,
      "neverChallenge": ["*/tools/*"],
      "minReadableLogs": 1,
      "exactReadableLogs": 3,
      "requireNoFailures": true,
      "expectUnsupported": 0,
      "unsupportedLabelIncludes": "アクセスログ",
      "minQuestions": 5,
      "fullReport": true
    }
  ]
}
```

| キー | 意味 |
|---|---|
| `profileDirs` | 読み込むプロファイルのフォルダ。相対パスはマニフェストの場所から解決 |
| `path` | アーカイブ。無ければその項目だけ skip（「確かめていない」を「合格」と見せない） |
| `profileId` | 自動判定で選ばれるべきプロファイル。他のプロファイルが強く一致しないことも見る |
| `credential` | `"embedded"`（既定）なら同梱の案内からパスワード候補を検出できることを確かめる |
| `requireBaseline` / `requireTool` | 平常時ログ／同梱ツールが見つかること |
| `neverChallenge` | 問題ログにしてはならないもののパターン |
| `minReadableLogs` / `exactReadableLogs` | 読み取れた問題ログの本数 |
| `requireNoFailures` | 読み取り失敗が無いこと |
| `expectUnsupported` / `unsupportedLabelIncludes` | 専用解析の無いログの数と表示名 |
| `minQuestions` | 設問の最少数 |
| `fullReport` | 導入・時系列・ATT&CK・未確定事項がそろうこと |

このほか、同じ入力から同じ教材ができること（ダイジェストで比較）、すべての証拠に
出典・行番号・原文があること、設問・時系列・ATT&CK が実在する証拠を指すこと、
正解が引用行から登録済みパーサーで読み直せることを、どのアーカイブにも確かめます。

### 7.2 失敗文に出さないもの

実データは再配布できないことが多いので、失敗しても次を出しません。

- パスワード、ログ本文、ZIP メンバー名、プロファイル ID、期待値の数
- アーカイブは「archive #2」のように**マニフェスト内の番号**で呼びます

検査はすべて真偽値だけを受け取る `_check()` を通します（`assertEqual` などは
比べた値を失敗文に載せるため使いません）。教材の同一性は SHA-256 のダイジェストで
比べます。`TestTheHarnessLeaksNothing` が、秘密を仕込んだ架空のマニフェストで
わざと失敗させ、失敗文に何も漏れないことを毎回確かめます。

## 8. リポジトリに置かないもの

- 実データ（配布 ZIP、展開物、ログ本文、パスワード、正解、ハッシュ値）
- 特定のデータセット向けのプロファイル、マニフェスト、データセット固有の手順書
  （置き場所の例: Git 管理外の `.local-validation/`。`.gitignore` 済み）

テストの fixture は、テストのために作った名前（`example-incident/`、`evidence/logs.zip`、
`reference/baseline.zip`、`tools/sample.log`）と文書用のアドレス（IPv4 は RFC 5737、
IPv6 は RFC 3849、MAC は RFC 7042）で、
実行時に組み立てます。
